# سناریوی Threat Hunting: یک Account در ساعت ۳ صبح روی چند Server وارد شده است

این سناریو برای مصاحبه‌ی SOC T2 مهم است، چون می‌تواند نشانه‌ی Lateral Movement، سوءاستفاده از حساب معتبر یا استفاده‌ی غیرمجاز از حساب ادمین باشد. از طرف دیگر، ممکن است یک Job زمان‌بندی‌شده، سرویس بکاپ یا عملیات نگهداری شبانه باشد.

نکته‌ی کلیدی در مصاحبه: ساعت ۳ صبح به‌تنهایی شاخص حمله نیست؛ الگوی دسترسی، نوع حساب، مبدأ اتصال و رفتار بعد از Login تعیین‌کننده‌اند.

## 1. Hunt Objective & Hypothesis — هدف و فرضیه

هدف من مشخص کردن این است که آیا ورود یک حساب به چند Server در یک بازه‌ی زمانی کوتاه، فعالیت مجاز بوده یا نشان‌دهنده‌ی دسترسی غیرعادی است.

فرضیه‌های اصلی:

- H1 — Lateral Movement: مهاجم با استفاده از اعتبارنامه‌ی یک حساب، از یک Server به Serverهای دیگر حرکت کرده است.
- H2 — سوءاستفاده از حساب معتبر: حساب کاربری یا ادمین به‌صورت غیرمجاز استفاده شده است.
- H3 — فعالیت مجاز مدیریتی: ادمین یا تیم زیرساخت عملیات نگهداری شبانه انجام داده‌اند.
- H4 — فعالیت سرویس یا اتوماسیون: یک Service Account یا ابزار مدیریت متمرکز، به‌صورت خودکار به چند Server متصل شده است.

در ابتدا به دنبال پاسخ چهار سؤال هستم:

1. آیا این حساب معمولاً در این ساعت فعالیت دارد؟
2. آیا ورودها به چند Server در فاصله‌ی زمانی غیرمعمول انجام شده‌اند؟
3. آیا مبدأ و روش احراز هویت با رفتار معمول حساب سازگار است؟
4. آیا بعد از ورود، فعالیتی مثل اجرای Process غیرعادی، دسترسی به منابع حساس یا تغییر تنظیمات دیده می‌شود؟

## 2. Telemetry & Data Sources — چه داده‌هایی لازم دارم؟

Windows Security Logs

Event ID 4624، 4625 و در صورت نیاز 4648

حساب هدف، زمان ورود، Logon Type، IP مبدأ، Workstation، Authentication Package و اطلاعات مربوط به نشست.

Server و Remote Access Telemetry

RDP، WinRM، SMB، VPN، Jump Server و EDR

برای فهمیدن مسیر اتصال، روش دسترسی از راه دور و اینکه کدام Server مبدأ ارتباط بوده است.

Post-Login Activity

Process Creation، سرویس‌ها، Taskها و تغییرات حساب

برای بررسی اینکه پس از ورود، چه فرمان‌ها یا برنامه‌هایی اجرا شده‌اند و آیا نشانه‌ای از حرکت جانبی یا Persistence وجود دارد.

رویدادهای مهم برای این سناریو:

| Event ID | کاربرد                                       |
| -------- | -------------------------------------------- |
| 4624     | ورود موفق                                    |
| 4625     | ورود ناموفق مرتبط با همان حساب یا مبدأ       |
| 4648     | تلاش برای استفاده از اعتبارنامه‌های صریح     |
| 4672     | اختصاص امتیازهای ویژه به یک نشست             |
| 4688     | ایجاد Process، در صورت فعال بودن Audit مربوط |

نکته: Event ID 4672 به‌تنهایی اثبات نمی‌کند حساب مورد سوءاستفاده قرار گرفته؛ فقط باید در کنار نشست و فعالیت‌های بعدی بررسی شود.

## 3. Hunt Execution & Queries — اجرای عملی Hunt

### مرحله‌ی اول: پیدا کردن ورودهای موفق یک حساب به چند Server

اگر لاگ‌های Windows Security در Microsoft Sentinel و جدول `SecurityEvent` موجود باشند، از این Query شروع می‌کنم:

```
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4624
| where isnotempty(TargetAccount)
| where TargetAccount !endswith "$"
| summarize
    LoginCount = count(),
    FirstLogin = min(TimeGenerated),
    LastLogin = max(TimeGenerated),
    SourceIPs = make_set(IpAddress, 20),
    LogonTypes = make_set(LogonType, 10)
    by TargetAccount, Computer,
       TimeWindow = bin(TimeGenerated, 30m)
| where LoginCount >= 1
| order by TimeWindow desc
```

این Query نمایی از ورودهای موفق هر حساب روی هر Server در پنجره‌های ۳۰ دقیقه‌ای می‌دهد. اما به‌تنهایی ثابت نمی‌کند یک حساب در همان پنجره روی چند Server وارد شده؛ برای آن باید نتایج را بین Serverها هم‌بسته کنیم.

### مرحله‌ی دوم: شناسایی ورودهای نزدیک به هم روی چند Server

در این نمونه، ورودهای موفق یک حساب را در بازه‌های ۳۰ دقیقه‌ای بررسی می‌کنم و فقط حساب‌هایی را نگه می‌دارم که در همان بازه به حداقل سه Server متفاوت وارد شده‌اند.

```
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4624
| where isnotempty(TargetAccount)
| where TargetAccount !endswith "$"
| summarize
    Servers = make_set(Computer, 50),
    ServerCount = dcount(Computer),
    LoginCount = count(),
    SourceIPs = make_set(IpAddress, 20),
    LogonTypes = make_set(LogonType, 10),
    FirstSeen = min(TimeGenerated),
    LastSeen = max(TimeGenerated)
    by TargetAccount, TimeWindow = bin(TimeGenerated, 30m)
| where ServerCount >= 3
| project
    TargetAccount,
    TimeWindow,
    ServerCount,
    Servers,
    LoginCount,
    SourceIPs,
    LogonTypes,
    FirstSeen,
    LastSeen
| order by FirstSeen desc
```

این Query یک Hunt اولیه است؛ مقدار سه Server و پنجره‌ی ۳۰ دقیقه‌ای صرفاً آستانه‌ی نمونه‌اند و باید با محیط سازمان تنظیم شوند. همچنین `bin()` مرزهای ثابت زمانی دارد و ممکن است یک توالی سریع از مرز دو پنجره عبور کند.

چرا ورود به چند Server مهم است؟ چون اگر یک حساب در فاصله‌ی کوتاهی به چند سیستم حساس متصل شود، مخصوصاً از یک مبدأ غیرمعمول، احتمال حرکت جانبی یا استفاده‌ی غیرمجاز از اعتبارنامه ارزش بررسی بیشتری پیدا می‌کند.

### مرحله‌ی سوم: بررسی اینکه ساعت ۳ صبح واقعاً غیرعادی است

قبل از اینکه ساعت را به‌عنوان شاخص مشکوک استفاده کنم، باید منطقه‌ی زمانی سازمان را مشخص کنم. `TimeGenerated` در Sentinel معمولاً UTC است؛ بنابراین ساعت 03:00 را مستقیماً از این فیلد بدون تبدیل منطقه‌ی زمانی تفسیر نمی‌کنم.

سپس الگوی تاریخی حساب را بررسی می‌کنم:

- آیا این حساب در هفته‌های گذشته هم در همین ساعت Login داشته؟
- آیا در همان ساعت، حساب‌های مشابه یا Service Accountهای دیگر هم فعال بوده‌اند؟
- آیا این Serverها در برنامه‌ی نگهداری شبانه قرار دارند؟
- آیا دسترسی‌ها از Jump Server یا ابزار مدیریتی شناخته‌شده آمده‌اند؟

هدف، مقایسه‌ی رفتار فعلی با Baseline همان حساب و همان نقش سازمانی است؛ نه اینکه هر ورود شبانه را مشکوک بدانیم.

## 4. Pivoting & Evidence Correlation — هم‌بسته‌سازی شواهد

پس از شناسایی حساب و Serverها، این مسیر را دنبال می‌کنم:

یک Account — ساعت 03:00

آیا زمان و الگوی دسترسی غیرمعمول است؟

چند Server — Event ID 4624

ترتیب زمانی، Logon Type و مبدأ اتصال

Source Host

آیا ورودها از یک دستگاه یا Jump Server آمده‌اند؟

Logon Type

آیا ورود تعاملی، شبکه‌ای یا Remote است؟

Privileged Activity

آیا نشست امتیاز ویژه یا دسترسی حساس داشته است؟

Post-Login

چه Processها یا تغییراتی بعد از ورود رخ داده‌اند؟

سؤالات اصلی من:

1. آیا تمام ورودها از یک IP یا دستگاه مبدأ انجام شده‌اند؟
2. آیا ورودها از طریق RDP، SMB، WinRM یا یک روش دیگر بوده‌اند؟
3. آیا حساب، حساب ادمین انسانی است یا Service Account؟
4. آیا پس از ورود به Serverها Processهای غیرعادی یا ابزارهای مدیریتی مشکوک اجرا شده‌اند؟
5. آیا همین الگو برای حساب‌های دیگر نیز مشاهده می‌شود؟

برای مثال، ورود یک ادمین از Jump Server مجاز به سه Server در زمان پنجره‌ی نگهداری، با ورود همان حساب از یک Workstation ناشناخته و سپس اجرای فرمان‌های غیرمعمول، دو وضعیت کاملاً متفاوت هستند.

## 5. Validation & Scope — اعتبارسنجی و تعیین گستره

در این مرحله می‌خواهم بفهمم آیا با یک عملیات مجاز روبه‌رو هستیم یا احتمال دسترسی غیرمجاز وجود دارد.

مواردی که بررسی می‌کنم:

- هویت و نقش حساب: آیا حساب مجاز به دسترسی به این Serverها بوده است؟
- مبدأ ورود: آیا IP متعلق به VPN، Jump Server یا دستگاه مدیریتی مورد اعتماد است؟
- توالی ورودها: آیا دسترسی‌ها به‌صورت زنجیره‌ای و غیرعادی از یک Server به Server دیگر انجام شده‌اند؟
- رفتار بعد از ورود: آیا Process غیرمعمول، تغییر حساب، ایجاد سرویس یا دسترسی به منابع حساس مشاهده شده است؟
- محدوده‌ی احتمالی: آیا حساب‌های دیگر یا Serverهای بیشتری درگیر بوده‌اند؟

اگر حساب Service Account باشد، بررسی می‌کنم که آیا اتصال‌های شبانه با وظیفه‌ی سرویس و برنامه‌ی زمان‌بندی آن تطابق دارند. اگر حساب ادمین انسانی باشد، سابقه‌ی دسترسی و تأیید عملیات برنامه‌ریزی‌شده اهمیت بیشتری پیدا می‌کند.

نکته‌ی مهم: چند Event ID 4624 فقط نشان می‌دهد ورودهای موفق ثبت شده‌اند. برای اثبات حرکت جانبی، باید نوع دسترسی و شواهد مربوط به ارتباط و فعالیت بین سیستم‌ها را نیز بررسی کرد.

## 6. MITRE ATT&CK Mapping — نگاشت احتمالی

| تکنیک                                 | چه زمانی قابل استفاده است؟                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------------- |
| T1078 — Valid Accounts                | وقتی شواهد استفاده‌ی غیرمجاز از یک حساب معتبر وجود داشته باشد.                              |
| T1021 — Remote Services               | وقتی شواهد نشان دهند مهاجم از سرویس‌های راه دور برای دسترسی به سیستم دیگر استفاده کرده است. |
| T1021.001 — Remote Desktop Protocol   | اگر دسترسی از طریق RDP تأیید شود.                                                           |
| T1021.002 — SMB/Windows Admin Shares  | اگر استفاده از SMB یا Administrative Share برای دسترسی بین سیستم‌ها تأیید شود.              |

نگاشت را بر اساس رفتار تأییدشده انجام می‌دهم؛ نه صرفاً بر اساس ساعت ورود یا تعداد Serverها. اگر روش دسترسی مشخص نباشد، تکنیک خاصی را قطعی اعلام نمی‌کنم.

## 7. Conclusion & Confidence — نتیجه‌گیری

نتیجه‌ی Hunt را به‌صورت دقیق گزارش می‌کنم:

- Suspicious: یک حساب در ساعت غیرمعمول روی چند Server وارد شده، اما دلیل فعالیت هنوز مشخص نیست.
- Likely Unauthorized Access: مبدأ یا الگوی دسترسی غیرعادی است و شواهد تکمیلی احتمال سوءاستفاده را تقویت می‌کنند.
- Confirmed Compromise: شواهد معتبر نشان می‌دهند حساب برای دسترسی غیرمجاز استفاده شده یا فعالیت مخرب مشخصی انجام داده است.

در گزارش نهایی، حساب، Serverها، زمان‌ها، مبدأ ورود، Logon Type، رفتار پس از ورود، محدودیت‌های لاگ و سطح اطمینان را ثبت می‌کنم.

## 8. Response & Detection Improvement — واکنش و بهبود Detection

اگر احتمال دسترسی غیرمجاز جدی باشد:

1. وضعیت حساب، نشست‌های فعال و سطح دسترسی آن را بررسی می‌کنم.
2. در صورت تأیید تهدید یا خطر فوری، حساب یا نشست‌ها را طبق رویه‌ی سازمان محدود می‌کنم.
3. Serverهای درگیر را برای اجرای Processهای مشکوک، ایجاد سرویس و سایر نشانه‌های حرکت جانبی بررسی می‌کنم.
4. بررسی را با همان حساب، مبدأ، بازه‌ی زمانی و الگوی دسترسی به سیستم‌های دیگر گسترش می‌دهم.
5. Detection را با ترکیب زمان غیرمعمول، تعداد Serverهای یکتا، نوع حساب، مبدأ جدید و رفتار پس از ورود بهبود می‌دهم.

یک Detection خوب صرفاً هشدار نمی‌دهد که «ورود ساعت ۳ صبح رخ داده است»؛ بلکه بررسی می‌کند آیا این ورود با نقش حساب، الگوی تاریخی و زمینه‌ی امنیتی آن سازگار است یا خیر.

## پاسخ کوتاه برای شروع جواب در مصاحبه

ابتدا Event ID 4624 را روی Serverهای موردنظر بررسی می‌کنم تا مشخص شود حساب در چه زمانی، از چه مبدأیی و با چه Logon Type وارد شده است. سپس الگوی دسترسی را با سابقه‌ی همان حساب و برنامه‌ی نگهداری سازمان مقایسه می‌کنم.

در مرحله‌ی بعد، بررسی می‌کنم آیا ورودها از یک مبدأ مشترک انجام شده‌اند، آیا حساب سطح دسترسی بالایی دارد و آیا این توالی با Lateral Movement سازگار است. سپس با بررسی رویدادهای 4672، 4688 و Telemetry مربوط به RDP، SMB یا WinRM، فعالیت پس از ورود را تحلیل می‌کنم.

در ادامه، Hunt را روی سایر Serverها و حساب‌ها گسترش می‌دهم و بر اساس شواهد، تکنیک‌های مرتبط MITRE ATT&CK را مشخص می‌کنم.

نکته‌ی مهم این است که ورود به چند Server در ساعت ۳ صبح به‌تنهایی اثبات‌کننده‌ی حمله نیست. برای اعلام Compromise باید شواهدی از دسترسی غیرمجاز یا رفتار مخرب داشته باشم و در صورت تأیید تهدید، اقدامات مهار و بهبود Detection را انجام دهم.
