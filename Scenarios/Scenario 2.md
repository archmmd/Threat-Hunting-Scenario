# سناریوی Threat Hunting: رویداد 4688 و اجرای `cmd.exe` توسط یک Process ناشناس

اگر در لاگ‌های ویندوز با Security Event ID 4688 مواجه شوم که نشان می‌دهد `cmd.exe` توسط یک Process ناشناس اجرا شده، آن را به‌عنوان یک سرنخ برای بررسی اجرای فرمان‌ها در سیستم در نظر می‌گیرم.

نکته کلیدی این است که Event ID 4688 مربوط به ایجاد یک Process جدید است؛ ناشناس بودن Process والد به‌تنهایی اثبات نمی‌کند که فعالیت مخرب است. ممکن است اطلاعات والد در لاگ موجود نباشد، مسیر یا نام فایل ثبت نشده باشد، یا پردازش متعلق به یک ابزار مشروع باشد.

هدف من این است که مشخص کنم چه پردازشی `cmd.exe` را اجرا کرده، چه فرمانی اجرا شده، رفتار بعدی چه بوده و آیا این رویداد بخشی از یک زنجیره مخرب است یا خیر.

## ۱. Hunt Objective & Hypothesis

هدف هانت

شناسایی منشأ اجرای `cmd.exe`، بررسی فرمان‌های اجراشده و تعیین ارتباط احتمالی با فعالیت مخرب.

فرضیه اصلی — H1

ممکن است یک Process غیرمجاز یا مخرب، `cmd.exe` را برای اجرای دستورات سیستم، اجرای اسکریپت یا پیشبرد فعالیت مهاجم راه‌اندازی کرده باشد.

فرضیه جایگزین — H2

ممکن است اجرای `cmd.exe` مربوط به یک ابزار مدیریتی، اسکریپت سازمانی، نصب نرم‌افزار یا فرایند مشروع دیگری باشد.

سؤال اصلی هانت: آیا می‌توان هویت Process والد و هدف فرمان اجراشده را با شواهد معتبر مشخص کرد؟

## ۲. Telemetry & Data Sources

در مرحله اول، Event ID 4688 را از Windows Security Log استخراج می‌کنم و در صورت امکان آن را با EDR و سایر لاگ‌ها همبسته می‌کنم.

| داده موردنیاز                             | کاربرد                                             |
| ----------------------------------------- | -------------------------------------------------- |
| `New Process Name`                        | مسیر Process جدید، یعنی `cmd.exe`                  |
| `Creator Process Name`                    | مسیر Process ایجادکننده، در صورت ثبت               |
| `Process Command Line`                    | فرمان اجراشده، در صورت فعال بودن ثبت Command Line  |
| `New Process ID`                          | شناسایی Process جدید                               |
| `Creator Process ID`                      | بررسی Process ایجادکننده                           |
| `Subject / Target Account`                | مشخص کردن حساب مرتبط با ایجاد Process              |
| `TimeCreated`                             | ساخت Timeline                                      |
| EDR Process Tree                          | بررسی رابطه والد و فرزند و فعالیت‌های مرتبط        |
| Windows Security و Sysmon                 | بررسی رویدادهای مکمل                               |
| PowerShell، Task Scheduler و Service Logs | بررسی منشأ احتمالی اجرای فرمان، در صورت مرتبط بودن |

### نکته مهم درباره Event ID 4688

برای مشاهده Command Line در این رویداد، باید سیاست Include command line in process creation events فعال باشد. همچنین ثبت Process Creation Auditing باید پیکربندی شده باشد.

اگر فیلد Command Line خالی است، نمی‌توان نتیجه گرفت که هیچ فرمانی اجرا نشده؛ ممکن است ثبت آن فعال نبوده باشد.

## ۳. Hunt Execution & Queries

### گام اول: بررسی جزئیات Event ID 4688

اگر به Windows Security Log دسترسی داشته باشم، ابتدا خود رویداد را بررسی می‌کنم؛ قبل از اینکه سراغ جست‌وجوی گسترده بروم.

نمونه Query با PowerShell:

```
$startTime = (Get-Date).AddHours(-24)

Get-WinEvent -FilterHashtable @{
    LogName   = 'Security'
    Id        = 4688
    StartTime = $startTime
} | ForEach-Object {
    $event = $_
    $data = [xml]$event.ToXml()

    $fields = @{}
    foreach ($item in $data.Event.EventData.Data) {
        $fields[$item.Name] = $item.'#text'
    }

    if ($fields['NewProcessName'] -match '\\cmd\.exe$') {
        [PSCustomObject]@{
            TimeCreated       = $event.TimeCreated
            NewProcessName    = $fields['NewProcessName']
            NewProcessId      = $fields['NewProcessId']
            CreatorProcess    = $fields['CreatorProcessName']
            CreatorProcessId  = $fields['ProcessId']
            CommandLine       = $fields['CommandLine']
            SubjectUser       = $fields['SubjectUserName']
            SubjectDomain     = $fields['SubjectDomainName']
        }
    }
} | Format-List
```

منطق این Query:

- رویدادهای ۲۴ ساعت اخیر را از Security Log می‌خواند.
- فقط رویدادهایی را نگه می‌دارد که Process جدید آن‌ها `cmd.exe` باشد.
- فیلدهای مهم را از XML رویداد استخراج می‌کند.
- نام و شناسه Process والد و Command Line را در صورت موجود بودن نمایش می‌دهد.

نکته فنی: این اسکریپت برای ساختار رایج Event ID 4688 نوشته شده است؛ باید نام فیلدها را با نسخه ویندوز و XML واقعی همان محیط تطبیق داد. اگر لاگ والد یا Command Line را ثبت نکرده باشد، این Query نمی‌تواند اطلاعات غایب را بازیابی کند.

### گام دوم: بررسی Process در Microsoft Defender XDR

اگر EDR من Microsoft Defender for Endpoint باشد، از جدول `DeviceProcessEvents` برای مشاهده Process ایجادشده و اطلاعات Process والد استفاده می‌کنم.

```
DeviceProcessEvents
| where Timestamp > ago(24h)
| where FileName =~ "cmd.exe"
| project
    Timestamp,
    DeviceName,
    AccountName,
    FolderPath,
    ProcessCommandLine,
    ProcessId,
    ProcessUniqueId,
    InitiatingProcessFileName,
    InitiatingProcessFolderPath,
    InitiatingProcessCommandLine,
    InitiatingProcessId,
    InitiatingProcessUniqueId,
    InitiatingProcessAccountName,
    SHA1
| order by Timestamp desc
```

این Query تمام اجرای‌های `cmd.exe` در بازه انتخابی را نشان می‌دهد؛ به همین دلیل، حتی اگر نام Process والد در Event ID 4688 ناقص باشد، ممکن است EDR اطلاعات بیشتری ارائه کند.

در خروجی دنبال این موارد می‌گردم:

- نام و مسیر Process والد
- Command Line پردازش والد
- حساب کاربری اجراکننده
- شناسه‌های پردازش برای همبستگی
- Hash و مسیر فایل والد، در صورت ثبت

اگر Process والد واقعاً مشخص نباشد، هنوز نباید آن را مخرب اعلام کنم؛ ابتدا بررسی می‌کنم که اطلاعات در EDR موجود است یا نه.

## ۴. Pivoting & Evidence Correlation

پس از پیدا کردن رویداد، بررسی را در سه مسیر ادامه می‌دهم.

Pivot A — بررسی Process والد

اگر والد مشخص باشد، مسیر فایل، امضای دیجیتال، Hash، Command Line و فرایندهای بالادستی آن را بررسی می‌کنم.

برای مثال، اگر والد `wscript.exe`، `mshta.exe` یا یک فایل اجرایی از مسیر موقت کاربر باشد، رفتار را دقیق‌تر بررسی می‌کنم. این نام‌ها به‌تنهایی اثبات مخرب بودن نیستند.

Pivot B — بررسی فرمان‌های اجراشده

به محتوای `ProcessCommandLine` توجه می‌کنم. برای مثال، آیا `cmd.exe` فقط یک دستور مدیریتی اجرا کرده یا زنجیره‌ای از فرمان‌ها را اجرا کرده است؟

فرمان‌هایی مانند `whoami`، `ipconfig`، `net user` یا `schtasks` باید با زمینه اجرا تحلیل شوند. این دستورات کاربرد مشروع هم دارند؛ اهمیت آن‌ها به توالی، حساب کاربری، میزبان و رفتارهای مرتبط بستگی دارد.

Pivot C — بررسی رفتار پس از اجرا

بررسی می‌کنم که آیا `cmd.exe` پردازش دیگری ایجاد کرده، فایل یا سرویس جدیدی به وجود آمده، ارتباط شبکه‌ای غیرعادی رخ داده یا نشانه‌ای از Persistence دیده می‌شود.

سپس همان رفتار را در سایر میزبان‌ها جست‌وجو می‌کنم تا مشخص شود با یک رویداد منفرد روبه‌رو هستیم یا یک الگوی تکرارشونده.

برای ارتباط دادن رویدادها، صرفاً به PID تکیه نمی‌کنم؛ PID ممکن است مجدداً استفاده شود. میزبان، زمان، شناسه یکتای Process در صورت وجود و جزئیات Process Tree را هم در نظر می‌گیرم.

## ۵. Validation & Scope

در این مرحله باید مشخص کنم «ناشناس» دقیقاً به چه معناست.

| وضعیت                                                  | برداشت صحیح                                        |
| ------------------------------------------------------ | -------------------------------------------------- |
| نام Process والد در لاگ ثبت نشده                       | نقص اطلاعات؛ نه اثبات فعالیت مخرب                  |
| Process والد وجود دارد ولی متعلق به ابزار ناشناخته است | نیازمند بررسی هویت و رفتار                         |
| والد از مسیر غیرمعمول اجرا شده و فرمان مشکوک دارد      | افزایش سطح ظن؛ نیازمند همبستگی بیشتر               |
| شواهد مستقل، اجرای مخرب را تأیید می‌کنند               | می‌توان فعالیت مخرب را تأیید کرد                   |
| همان الگو در چند میزبان دیده می‌شود                    | بررسی دامنه‌ای و احتمال فعالیت گسترده‌تر ضروری است |

برای Scope، میزبان‌های دیگر را با الگوی Process والد، Command Line، Hash، حساب کاربری و بازه زمانی جست‌وجو می‌کنم. همچنین مشخص می‌کنم آیا شواهد برای انتساب رویداد به یک زنجیره حمله کافی است یا هنوز توضیح مشروعی محتمل است.

## ۶. MITRE ATT&CK Mapping

برای این سناریو، تکنیک اصلی احتمالی عبارت است از:

| تکنیک                                     | چه زمانی قابل انتساب است؟                                                    |
| ----------------------------------------- | ---------------------------------------------------------------------------- |
| T1059.003 — Windows Command Shell         | وقتی شواهد نشان دهند `cmd.exe` برای اجرای فرمان‌ها استفاده شده است.          |
| T1059 — Command and Scripting Interpreter | برای طبقه‌بندی کلی‌تر استفاده از مفسر فرمان، در صورت تناسب با شواهد          |
| T1053 — Scheduled Task/Job                | اگر شواهد نشان دهند از Task زمان‌بندی‌شده برای اجرای فعالیت استفاده شده است. |
| T1036 — Masquerading                      | فقط اگر شواهدی از جعل هویت یا ظاهر فایل و پردازش وجود داشته باشد.            |

صرف مشاهده Event ID 4688 به معنی وقوع تمام این تکنیک‌ها نیست. نگاشت دقیق باید بر اساس رفتار تأییدشده انجام شود.

## ۷. Conclusion & Confidence

با اطلاعات اولیه فعلی، فقط می‌توانم بگویم ایجاد `cmd.exe` ثبت شده و منشأ اجرای آن نیازمند بررسی است.

نتیجه موقت من:

- Observed: ایجاد `cmd.exe` در Event ID 4688 ثبت شده است.
- Unresolved: هویت و ماهیت Process والد هنوز مشخص نیست.
- Next step: بازیابی اطلاعات Process والد، تحلیل Command Line و بررسی رفتارهای مرتبط.
- Scope: هنوز مشخص نیست رویداد منفرد است یا بخشی از فعالیت گسترده‌تر.

تا زمانی که شواهد کافی ندارم، این رویداد را نه قطعی مخرب اعلام می‌کنم و نه بی‌خطر.

## ۸. Response & Detection Improvement

اگر شواهد اجرای مخرب را تأیید کنند، بر اساس شدت و فعال بودن تهدید، اقدامات مهار و ارجاع به Incident Response را انجام می‌دهم.

از منظر Detection Engineering نیز پیشنهاد می‌کنم:

- برای Event ID 4688، ثبت Command Line را فعال و صحت آن را بررسی کنیم.
- رویدادهای Process Creation را با EDR و سایر منابع همبسته کنیم.
- روی ترکیب Process والد غیرمعمول، Command Line مشکوک و رفتارهای بعدی Detection بسازیم.
- Rule را با فعالیت‌های مشروع مدیریتی آزمایش کنیم تا False Positive کاهش یابد.
- برای رویدادهایی که اطلاعات والد در آن‌ها ناقص است، Gapهای Telemetry را مستند کنیم.

## پاسخ کوتاه برای شروع جواب در مصاحبه

ابتدا Event ID 4688 را به‌عنوان یک سیگنال برای بررسی ایجاد Process تحلیل می‌کنم. ناشناس بودن Process والد به‌تنهایی به معنی مخرب بودن فعالیت نیست.

در مرحله اول، نام و مسیر Process والد، Command Line، شناسه‌های Process، حساب کاربری و Timestamp را بررسی می‌کنم. اگر اطلاعات کافی در Security Log وجود نداشته باشد، از EDR و Process Tree برای تکمیل شواهد استفاده می‌کنم.

سپس فرمان‌های اجراشده توسط cmd.exe، پردازش‌های فرزند، فعالیت فایل و ارتباطات شبکه را بررسی می‌کنم تا مشخص شود این رویداد چه رفتاری را دنبال کرده است.

در ادامه، بر اساس Process والد، Command Line، Hash و الگوی رفتاری، جست‌وجو را به سایر میزبان‌ها گسترش می‌دهم. در نهایت، شواهد را اعتبارسنجی می‌کنم و فقط در صورت وجود شواهد کافی، فعالیت را مخرب اعلام می‌کنم. اگر رفتار مخرب تأیید شود، اقدامات مهار و بهبود Detection را متناسب با شدت رخداد پیشنهاد می‌دهم.
