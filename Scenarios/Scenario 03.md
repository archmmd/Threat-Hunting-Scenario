# سناریوی Threat Hunting: شناسایی `rundll32.exe` مشکوک در Sysmon Event ID 1

اگر در Sysmon Event ID 1 یک اجرای مشکوک از `rundll32.exe` ببینم، بررسی را با این اصل شروع می‌کنم:

`rundll32.exe` یک ابزار معتبر ویندوز است، اما می‌تواند برای اجرای کد DLL و پنهان کردن فعالیت مخرب در قالب یک فرایند سیستمی استفاده شود. بنابراین، نام فایل به‌تنهایی نه نشانه قطعی بدافزار است و نه دلیل بی‌خطر بودن آن.

هدف من این است که مشخص کنم چه پردازشی `rundll32.exe` را اجرا کرده، چه DLL یا تابعی هدف قرار گرفته، فایل از کجا آمده و آیا شواهدی از اجرای کد مخرب یا رفتارهای پس از اجرا وجود دارد.

## ۱. Hunt Objective & Hypothesis

هدف هانت

بررسی اجرای `rundll32.exe`، شناسایی DLL یا محتوای هدف و تعیین ارتباط احتمالی آن با فعالیت مخرب.

فرضیه اصلی — H1

ممکن است `rundll32.exe` برای اجرای کد مخرب از طریق یک DLL یا روش غیرمعمول فراخوانی شده باشد.

فرضیه جایگزین — H2

ممکن است اجرای آن مربوط به یک برنامه مشروع، کامپوننت ویندوز، نصب نرم‌افزار یا فعالیت مدیریتی مجاز باشد.

سؤال اصلی: آیا مسیر اجرا، Command Line، DLL هدف و رفتارهای بعدی با یک فعالیت مشروع سازگارند یا زنجیره‌ای از شواهد مشکوک را تشکیل می‌دهند؟

## ۲. Telemetry & Data Sources

من ابتدا Sysmon Event ID 1 را بررسی می‌کنم و سپس در صورت نیاز سراغ EDR و لاگ‌های تکمیلی می‌روم.

| داده                | اهمیت                                             |
| ------------------- | ------------------------------------------------- |
| `Image`             | مسیر فایل اجرایی `rundll32.exe`                   |
| `CommandLine`       | DLL، تابع یا آرگومان‌های مورد استفاده             |
| `ParentImage`       | پردازش والد                                       |
| `ParentCommandLine` | زمینه اجرای پردازش والد                           |
| `ProcessGuid`       | همبستگی دقیق‌تر رویدادهای همان پردازش             |
| `ParentProcessGuid` | ارتباط با پردازش والد                             |
| `User` و `UtcTime`  | حساب کاربری و زمان اجرا                           |
| `Hashes`            | بررسی Hash فایل اجرایی                            |
| `CurrentDirectory`  | مسیر کاری پردازش                                  |
| Sysmon Event ID 7   | اطلاعات بارگذاری Image/DLL، اگر پیکربندی شده باشد |
| Sysmon Event ID 3   | ارتباط شبکه‌ای، در صورت فعال بودن                 |
| EDR و لاگ‌های فایل  | بررسی DLL، فرایندهای فرزند و رفتارهای مرتبط       |

نکته مهم: Sysmon Event ID 1 به‌تنهایی اثبات نمی‌کند که یک DLL خاص با موفقیت بارگذاری شده یا کد آن اجرا شده است. برای این نتیجه به شواهد مکمل نیاز داریم.

## ۳. Hunt Execution & Queries

### گام اول: استخراج اجرای مشکوک از Sysmon Event ID 1

اگر به لاگ‌های Sysmon دسترسی داشته باشم، ابتدا `rundll32.exe` را در بازه زمانی موردنظر جست‌وجو می‌کنم.

```
$startTime = (Get-Date).AddHours(-24)

Get-WinEvent -FilterHashtable @{
    LogName   = 'Microsoft-Windows-Sysmon/Operational'
    Id        = 1
    StartTime = $startTime
} | ForEach-Object {
    $event = $_
    $xml = [xml]$event.ToXml()
    $fields = @{}

    foreach ($item in $xml.Event.EventData.Data) {
        $fields[$item.Name] = $item.'#text'
    }

    if ($fields['Image'] -match '\\rundll32\.exe$') {
        [PSCustomObject]@{
            TimeCreated      = $event.TimeCreated
            Image            = $fields['Image']
            CommandLine      = $fields['CommandLine']
            ParentImage      = $fields['ParentImage']
            ParentCommandLine = $fields['ParentCommandLine']
            ProcessGuid      = $fields['ProcessGuid']
            ParentProcessGuid = $fields['ParentProcessGuid']
            User             = $fields['User']
            Hashes           = $fields['Hashes']
            CurrentDirectory = $fields['CurrentDirectory']
        }
    }
} | Format-List
```

چه چیزی از این Query می‌خواهم؟

- مسیر واقعی `rundll32.exe` چیست؟
- چه DLL یا آرگومانی در Command Line دیده می‌شود؟
- کدام Process آن را اجرا کرده؟
- آیا اجرای آن با زمان، کاربر و فعالیت‌های دیگر سازگار است؟
- آیا Process GUID برای Pivot کردن به رویدادهای دیگر موجود است؟

این جست‌وجو اجرای‌های ثبت‌شده در Sysmon را نشان می‌دهد؛ اگر Sysmon فعال نبوده یا رویدادها حذف شده باشند، ممکن است تصویر کاملی از فعالیت نداشته باشیم.

### گام دوم: بررسی Command Line و DLL هدف

بعد از استخراج رویداد، Command Line را به‌دقت تحلیل می‌کنم.

برای مثال، این موارد ارزش بررسی بیشتر دارند:

| نشانه                                            | چرا مهم است؟                                             |
| ------------------------------------------------ | -------------------------------------------------------- |
| DLL در مسیر `AppData`، `Temp` یا پوشه کاربر      | ممکن است فایل خارج از مسیرهای متعارف برنامه نصب شده باشد |
| DLL در مسیر شبکه‌ای یا Share                     | ممکن است کد از یک منبع شبکه اجرا شده باشد                |
| آرگومان‌های غیرمعمول یا نام‌گذاری مبهم           | ممکن است تلاش برای پنهان‌کردن هدف واقعی اجرا باشد        |
| استفاده از `javascript:` یا اجزای غیرمعمول Shell | ممکن است نشان‌دهنده روش متفاوتی برای اجرای کد باشد       |
| DLL با امضا یا ناشر نامشخص                       | نیازمند اعتبارسنجی بیشتر است                             |
| والد غیرمعمول مانند Office یا یک اسکریپت ناشناس  | می‌تواند زنجیره اجرای مشکوک را تقویت کند                 |

هیچ‌کدام از این نشانه‌ها به‌تنهایی حکم قطعی نیستند. برای نمونه، یک DLL در `AppData` ممکن است متعلق به برنامه‌ای مشروع باشد و یک DLL امضاشده نیز لزوماً بی‌خطر نیست.

اگر مسیر DLL در Command Line مشخص باشد، مسیر، Hash، امضای دیجیتال، زمان ایجاد و منشأ فایل را بررسی می‌کنم. اگر DLL هدف مشخص نباشد، از Command Line و شواهد بارگذاری ماژول در EDR یا Sysmon Event ID 7 کمک می‌گیرم.

### گام سوم: بررسی Process Tree در Microsoft Defender XDR

اگر EDR من Microsoft Defender for Endpoint باشد، این Query اجرای‌های `rundll32.exe` و اطلاعات والد را نشان می‌دهد:

```
DeviceProcessEvents
| where Timestamp > ago(24h)
| where FileName =~ "rundll32.exe"
| project
    Timestamp,
    DeviceName,
    AccountName,
    FolderPath,
    ProcessCommandLine,
    ProcessId,
    ProcessUniqueId,
    InitiatingProcessFileName,
    InitiatingProcessFolderPath,
    InitiatingProcessCommandLine,
    InitiatingProcessId,
    InitiatingProcessUniqueId,
    SHA1
| order by Timestamp desc
```

از این Query برای تکمیل اطلاعاتی استفاده می‌کنم که در Sysmon وجود ندارد یا به‌سادگی قابل جست‌وجو نیست.

نکته فنی: Process Tree فقط زنجیره‌ای از پردازش‌ها را نشان می‌دهد؛ برای اثبات اجرای موفق کد داخل DLL باید شواهد متناسب دیگری هم داشته باشم.

## ۴. Pivoting & Evidence Correlation

پس از بررسی Command Line، سه Pivot اصلی انجام می‌دهم.

Pivot A — بررسی DLL

اگر DLL مشخص باشد، Hash، امضای دیجیتال، مسیر، زمان ایجاد و منشأ آن را بررسی می‌کنم. سپس به دنبال همان Hash یا مسیر در سایر میزبان‌ها می‌گردم.

اگر فایل در دسترس باشد، آن را در محیط تحلیل ایزوله بررسی می‌کنم و بدون نیاز، آن را اجرا نمی‌کنم.

Pivot B — بررسی والد و فرزندان

Process والد را به عقب دنبال می‌کنم تا منشأ اجرای `rundll32.exe` مشخص شود. سپس بررسی می‌کنم آیا این پردازش، فرایند دیگری ایجاد کرده یا فعالیت فایل و Registry غیرمعمولی داشته است.

اگر والد `winword.exe`، `powershell.exe` یا یک Process ناشناس باشد، آن را با شواهد مستقل بررسی می‌کنم؛ صرف نام والد برای نتیجه‌گیری کافی نیست.

Pivot C — شبکه و رفتار پس از اجرا

در Sysmon Event ID 3 یا Telemetry شبکه EDR بررسی می‌کنم که آیا پردازش با مقصدی خارجی ارتباط برقرار کرده است. همچنین Event ID 7 را برای شواهد بارگذاری Image یا DLL بررسی می‌کنم.

با استفاده از Process GUID، میزبان و زمان، رویدادها را به هم مرتبط می‌کنم. اگر ارتباط شبکه یا بارگذاری DLL ثبت نشده باشد، این فقدان را اثبات نبودن رفتار تلقی نمی‌کنم.

## ۵. Validation & Scope

در این مرحله، یافته‌ها را اعتبارسنجی می‌کنم و بررسی را به یک میزبان محدود نمی‌کنم.

| سؤال                                       | شواهد موردنیاز                                     |
| ------------------------------------------ | -------------------------------------------------- |
| آیا `rundll32.exe` معتبر است؟              | مسیر فایل، Hash و امضای دیجیتال                    |
| آیا اجرای آن غیرمعمول است؟                 | Command Line، Process والد و الگوی معمول میزبان    |
| آیا DLL مشکوک است؟                         | مسیر، Hash، امضا، منشأ و تحلیل فایل                |
| آیا کد واقعاً اجرا شده؟                    | شواهد اجرای معتبر، رفتار پردازش و Telemetry تکمیلی |
| آیا فعالیت در میزبان‌های دیگر تکرار شده؟   | جست‌وجو بر اساس Hash، مسیر، Command Line و رفتار   |
| آیا ارتباط خارجی به همین فعالیت مربوط است؟ | همبستگی پردازش، زمان، مقصد و شواهد شبکه            |

اگر اجرای مشکوک تأیید شود، به دنبال همان الگوی رفتاری در سایر Endpointها می‌گردم. در Threat Hunting نباید تنها به یک Hash یا IP متکی بود؛ مهاجم ممکن است آن‌ها را تغییر دهد.

## ۷. Conclusion & Confidence

با مشاهده اولیه Sysmon Event ID 1، نتیجه من این است که یک اجرای `rundll32.exe` نیازمند بررسی شناسایی شده است؛ اما هنوز نمی‌توان گفت DLL مخرب بوده یا کد مخرب با موفقیت اجرا شده است.

برای رسیدن به نتیجه، باید سه موضوع را روشن کنم:

1. Execution: چه DLL یا هدفی فراخوانی شده و آیا اجرای موردنظر تأیید می‌شود؟
2. Behavior: پردازش قبل و بعد از اجرا چه رفتاری داشته است؟
3. Scope: آیا شواهد به یک میزبان محدودند یا الگوی مشابه در سیستم‌های دیگر وجود دارد؟

اگر شواهد مستقل اجرای مخرب را تأیید کنند، رویداد را به‌عنوان فعالیت مخرب طبقه‌بندی می‌کنم و بر اساس شدت آن، مهار و Incident Response را در اولویت قرار می‌دهم.

## ۸. Response & Detection Improvement

اگر فعالیت مخرب تأیید شود:

- شواهد Endpoint و فایل DLL را حفظ می‌کنم.
- در صورت فعال بودن تهدید، مطابق رویه سازمانی برای مهار میزبان یا فرایند اقدام می‌کنم.
- بررسی می‌کنم آیا همان DLL یا الگوی اجرا در میزبان‌های دیگر وجود دارد.
- Detection را بر اساس ترکیب مسیر DLL، Command Line، Process والد و رفتارهای پس از اجرا بهبود می‌دهم.
- Rule را با فعالیت‌های مشروع آزمایش می‌کنم تا False Positive کاهش پیدا کند.

برای Detection Engineering، بهتر است صرفاً روی اجرای `rundll32.exe` هشدار نسازیم؛ این ابزار در سیستم‌های سالم هم استفاده می‌شود. ترکیب چند سیگنال، زمینه دقیق‌تری برای تشخیص فراهم می‌کند.

## پاسخ کوتاه برای شروع جواب در مصاحبه

ابتدا Sysmon Event ID 1 را بررسی می‌کنم تا Command Line، مسیر فایل، Process والد، شناسه‌های پردازش و حساب کاربری را استخراج کنم. اجرای rundll32.exe به‌تنهایی اثبات فعالیت مخرب نیست؛ بنابراین تمرکز اصلی من روی DLL هدف و زمینه اجرای آن است.

سپس مسیر، Hash، امضای دیجیتال و منشأ DLL را بررسی می‌کنم و با Process Tree مشخص می‌کنم چه پردازشی rundll32.exe را اجرا کرده است. در ادامه، Sysmon Event ID 7، رویدادهای شبکه و Telemetry مربوط به فایل و پردازش را برای شناسایی رفتارهای بعدی بررسی می‌کنم.

بعد با Pivot کردن بر اساس Process GUID، Hash، Command Line و رفتار مشابه، جست‌وجو را به سایر میزبان‌ها گسترش می‌دهم. در نهایت، فقط بر اساس شواهد معتبر درباره مخرب بودن فعالیت تصمیم می‌گیرم و در صورت تأیید تهدید، اقدامات مهار و بهبود Detection را پیشنهاد می‌کنم.
