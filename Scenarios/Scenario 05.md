# سناریوی Threat Hunting: اجرای PowerShell با `-EncodedCommand`

این سناریو در مصاحبه‌ی SOC T2 و Threat Hunter مهم است، چون مهاجم می‌تواند از PowerShell برای اجرای دستورات، دریافت Payload، اجرای اسکریپت و برقراری ارتباط با زیرساخت خارجی استفاده کند؛ در حالی که `-EncodedCommand` ممکن است محتوای واقعی دستور را در نگاه اول پنهان کند.

اصل کلیدی: استفاده از `-EncodedCommand` به‌تنهایی نشانه‌ی قطعی بدافزار نیست. باید محتوای رمزگذاری‌شده را Decode کنیم، رفتار واقعی را بفهمیم و آن را با شواهد سیستم و شبکه تطبیق دهیم.

## 1. Hunt Objective & Hypothesis — هدف و فرضیه

می‌خواهم مشخص کنم PowerShell با چه هدفی اجرا شده و آیا فعالیت آن مخرب بوده است.

- H1 — اجرای فرمان مخرب: محتوای Decodeشده شامل دستورات مشکوک، اجرای کد یا تغییرات غیرمجاز است.
- H2 — دریافت Payload: اسکریپت از اینترنت یا یک منبع داخلی فایل یا کد دریافت می‌کند.
- H3 — اجرای کد در حافظه: اسکریپت تلاش می‌کند کد را بدون ذخیره‌سازی معمول فایل روی دیسک اجرا کند.
- H4 — استفاده‌ی مجاز: اسکریپت متعلق به ابزار مدیریتی، نرم‌افزار سازمانی یا فرایند اتوماسیون معتبر است.

در این مرحله فرضیه‌ها را قطعی نمی‌دانم؛ باید شواهد لازم برای تأیید یا رد هرکدام را پیدا کنم.

## 2. Telemetry & Data Sources — چه داده‌هایی جمع می‌کنم؟

Process Creation

Sysmon Event ID 1، Windows Event ID 4688، EDR

Command Line کامل، مسیر `powershell.exe` یا `pwsh.exe`، Process والد، کاربر، زمان اجرا و شناسه‌ی Process.

PowerShell Logs

PowerShell Operational، Event ID 4104 و 4103

در صورت فعال بودن Logging، برای بررسی Script Block و جزئیات اجرای دستورات.

Network & File Telemetry

EDR، Sysmon Event ID 3، DNS، Proxy و File Events

برای شناسایی مقصد خارجی، دانلود فایل، ارتباطات بعدی و آثار باقی‌مانده روی سیستم.

نکته‌ی مصاحبه‌ای: Event ID 4104 برای Script Block Logging است و در صورت فعال بودن تنظیم مربوطه می‌تواند محتوای اسکریپت را نشان دهد. نبود این رویداد به معنی اجرا نشدن PowerShell نیست.

## 3. Hunt Execution & Queries — اجرای عملی Hunt

### مرحله‌ی اول: پیدا کردن PowerShellهای دارای `EncodedCommand`

در Microsoft Defender XDR از این Query شروع می‌کنم:

```
DeviceProcessEvents
| where Timestamp > ago(24h)
| where FileName in~ ("powershell.exe", "pwsh.exe")
| where ProcessCommandLine matches regex
    @"(?i)(-enc(odedcommand)?\b|-e\s+[A-Za-z0-9+/]{8,}={0,2})"
| project
    Timestamp,
    DeviceName,
    AccountName,
    FileName,
    FolderPath,
    ProcessCommandLine,
    ProcessId,
    ProcessUniqueId,
    InitiatingProcessFileName,
    InitiatingProcessCommandLine,
    InitiatingProcessUniqueId,
    SHA1
| order by Timestamp desc
```

این Query برای شروع مفید است، اما کامل و بدون خطا نیست: شکل‌های کوتاه‌شده‌ی پارامتر PowerShell، فاصله‌گذاری‌های مختلف و تفاوت‌های Command Line ممکن است نیازمند تنظیم Query باشند. همچنین بعضی شکل‌های مشکوک با این الگو شناسایی نمی‌شوند.

هنگام بررسی نتیجه به این موارد توجه می‌کنم:

- آیا والد Process یک برنامه‌ی Office، مرورگر، اسکریپت یا Process ناشناس است؟
- آیا کاربر اجراکننده انتظار اجرای PowerShell را داشته است؟
- آیا آرگومان‌های دیگری مثل `-NoProfile`، `-WindowStyle Hidden` یا `-ExecutionPolicy Bypass` دیده می‌شوند؟
- آیا Process پس از اجرا اتصال شبکه‌ای برقرار کرده یا فایل جدیدی ساخته است؟

هیچ‌کدام از این آرگومان‌ها به‌تنهایی اثبات‌کننده‌ی فعالیت مخرب نیستند؛ اهمیت آن‌ها به زمینه‌ی اجرا بستگی دارد.

### مرحله‌ی دوم: Decode کردن محتوای `EncodedCommand`

پارامتر `-EncodedCommand` در PowerShell ویندوز معمولاً محتوای فرمان را به‌صورت Base64 از متن UTF-16LE دریافت می‌کند. بنابراین، برای تحلیل اولیه می‌توان از این روش استفاده کرد.

اگر مقدار Base64 را از لاگ استخراج کرده‌ام، روی یک سیستم تحلیل ایزوله می‌توانم این کد را اجرا کنم:

```
$encoded = "BASE64_VALUE_HERE"

$bytes = [Convert]::FromBase64String($encoded)

$decoded = [Text.Encoding]::Unicode.GetString($bytes)

$decoded
```

این کد فقط محتوا را Decode و چاپ می‌کند؛ دستور Decodeشده را اجرا نمی‌کند.

هنگام تحلیل، خروجی را مستقیماً در PowerShell اجرا نکن. ابتدا آن را به‌عنوان متن بررسی کن. همچنین ممکن است محتوای Decodeشده خودش شامل یک لایه‌ی Base64 دیگر، فشرده‌سازی، رشته‌های تکه‌تکه‌شده یا رمزگذاری دیگری باشد.

پس از Decode، دنبال رفتارهایی مانند این می‌گردم:

- `DownloadString`، `Invoke-WebRequest` یا `Start-BitsTransfer` برای دریافت محتوا
- `Invoke-Expression` یا `IEX` برای تفسیر و اجرای رشته
- استفاده از `FromBase64String` برای Decode مجدد
- دسترسی به Registry، ایجاد Scheduled Task یا تغییر تنظیمات امنیتی
- دستورات مربوط به جمع‌آوری اطلاعات سیستم، دسترسی به اعتبارنامه‌ها یا ارتباط شبکه‌ای

این‌ها سرنخ‌های تحلیلی هستند؛ وجود یک کلمه یا تابع به‌تنهایی اثبات حمله نیست.

### مرحله‌ی سوم: بررسی Script Block Logging

اگر PowerShell Script Block Logging فعال بوده، در Windows Event Log مسیر زیر را بررسی می‌کنم:

`Microsoft-Windows-PowerShell/Operational`

رویداد مهم:

- Event ID 4104: محتوای Script Block ثبت‌شده؛ ممکن است در چند رویداد یا قطعه ثبت شود.
- Event ID 4103: جزئیات Module Logging، در صورتی که پیکربندی مربوطه فعال باشد.

مزیت این مرحله آن است که ممکن است محتوای واقعی دستور را حتی زمانی که Command Line فقط رشته‌ی Base64 را نشان می‌دهد، در اختیارمان قرار دهد. البته ثبت کامل محتوا تضمین‌شده نیست و باید قطعه‌های مربوط به یک Script Block را با دقت کنار هم قرار داد.

## 4. Pivoting & Evidence Correlation — هم‌بسته‌سازی شواهد

بعد از Decode، تمرکز Hunt از «پارامتر مشکوک» به «رفتار واقعی اسکریپت» تغییر می‌کند.

PowerShell Process

Command Line، کاربر و Process والد

Decoded Command + Script Logs

هدف دستور و رفتار واقعی

Network

مقصد، زمان و Process مرتبط

File & Process

فایل‌های ساخته‌شده و فرزندان

برای مثال، فرض کن دستور Decodeشده شامل دریافت محتوا از یک دامنه‌ی خارجی و سپس تلاش برای اجرای آن در حافظه است. در این صورت:

1. رویدادهای شبکه را در بازه‌ی زمانی اجرای PowerShell بررسی می‌کنم.
2. مشخص می‌کنم اتصال واقعاً به همان Process تعلق داشته یا فقط در همان زمان روی میزبان رخ داده است.
3. مقصد را از نظر اعتبار، سابقه و ارتباط با فعالیت سازمان بررسی می‌کنم.
4. فرایندهای فرزند، فایل‌های ایجادشده و رفتارهای بعدی را بررسی می‌کنم.
5. با Hash، دامنه، IP، Command Line و الگوی رفتاری، سایر میزبان‌ها را Hunt می‌کنم.

در این مرحله باید بین سه ادعا تفاوت بگذارم: «اسکریپت تلاش کرده فایل دانلود کند»، «فایل واقعاً دانلود شده» و «فایل دانلودشده با موفقیت اجرا شده است». هرکدام به شواهد جداگانه نیاز دارند.

## 5. Validation & Scope — اعتبارسنجی و تعیین گستره

برای جلوگیری از نتیجه‌گیری اشتباه، این موارد را بررسی می‌کنم:

- منشأ اجرا: آیا اجرای PowerShell از طرف ابزار مدیریتی معتبر، اسکریپت سازمانی یا فعالیت کاربر انتظار می‌رفته است؟
- محتوای Decodeشده: آیا دستور واقعاً رفتاری مخرب دارد یا صرفاً برای پنهان‌سازی متن یا انتقال امن پارامترها استفاده شده است؟
- شواهد مستقل: آیا EDR، Script Block Logging، شبکه یا رویدادهای فایل، رفتار مورد ادعا را تأیید می‌کنند؟
- گستره‌ی حمله: آیا همان اسکریپت، Hash یا مقصد در دستگاه‌های دیگر نیز دیده شده است؟
- کامل بودن داده‌ها: آیا Logging فعال بوده و بازه‌ی زمانی مورد بررسی پوشش کافی دارد؟

اگر Script Block Logging فعال نبوده، این محدودیت را در نتیجه ثبت می‌کنم و برای بازسازی رفتار از Command Line، EDR و شواهد شبکه استفاده می‌کنم؛ نبود لاگ را معادل نبود رفتار نمی‌دانم.

نکته‌ی مهم: وجود `-EncodedCommand` به‌تنهایی برای نتیجه‌گیری قطعی درباره‌ی T1027 کافی نیست. همچنین اگر صرفاً دستور دانلود را ببینم، نباید ادعا کنم دانلود موفق بوده است.

## 7. Conclusion & Confidence — نتیجه‌گیری

نتیجه‌ی Hunt را متناسب با شواهد گزارش می‌کنم:

- Suspicious: PowerShell با `-EncodedCommand` اجرا شده، اما محتوای دستور یا رفتار بعدی برای تأیید فعالیت مخرب کافی نیست.
- Likely Malicious: محتوای Decodeشده و چند رفتار مستقل، مانند اتصال غیرمنتظره و تلاش برای اجرای Payload، با فعالیت مخرب سازگارند؛ هنوز برخی شواهد نیازمند تأیید هستند.
- Confirmed Malicious: شواهد معتبر، مانند Payload مخرب تأییدشده یا اجرای رفتار مخرب قابل انتساب به همان Process، نتیجه را پشتیبانی می‌کنند.

در گزارش نهایی، محتوای اصلی و Decodeشده، میزبان، کاربر، Process والد، زمان، مقصد شبکه، شواهد پشتیبان و محدودیت‌های بررسی را ثبت می‌کنم.

## 8. Response & Detection Improvement — واکنش و بهبود Detection

اگر تهدید تأیید شود یا شواهد معتبر از خطر فوری حکایت کنند:

- شواهد EDR و لاگ‌ها را حفظ می‌کنم.
- در صورت نیاز، میزبان را مطابق رویه‌ی Incident Response سازمان مهار می‌کنم.
- در صورت شناسایی مقصد مخرب، ارتباط مربوط را کنترل یا مسدود می‌کنم.
- سایر میزبان‌ها را برای همان اسکریپت، Hash، مقصد و الگوی رفتاری بررسی می‌کنم.
- Detection را بر اساس ترکیبی از `EncodedCommand`، Process والد، محتوای اسکریپت، مقصد شبکه و رفتار پس از اجرا بهبود می‌دهم.

هدف این است که Detection فقط به وجود `-EncodedCommand` وابسته نباشد؛ چون این کار می‌تواند False Positive زیادی تولید کند و در عین حال روش‌های دیگر اجرای PowerShell را از دست بدهد.

## پاسخ کوتاه برای شروع جواب در مصاحبه

ابتدا رویداد ایجاد Process را بررسی می‌کنم تا Command Line کامل، Process والد، حساب کاربری و زمان اجرا مشخص شود. سپس مقدار EncodedCommand را با فرض UTF-16LE و بدون اجرای محتوا Decode می‌کنم تا هدف واقعی دستور مشخص شود.

در مرحله‌ی بعد، Script Block Logging، به‌خصوص Event ID 4104، و Telemetry مربوط به شبکه و فایل را بررسی می‌کنم تا بفهمم اسکریپت چه رفتاری داشته و آیا اتصال خارجی یا اجرای Payload واقعاً اتفاق افتاده است.

سپس با Pivot کردن روی Process، Hash، مقصد شبکه و الگوی رفتاری، گستره‌ی فعالیت را روی سایر میزبان‌ها بررسی می‌کنم و در صورت نیاز نگاشت MITRE ATT&CK را انجام می‌دهم.

نکته‌ی مهم این است که EncodedCommand به‌تنهایی اثبات‌کننده‌ی بدافزار نیست؛ تصمیم نهایی را بر اساس محتوای دستور و شواهد هم‌بسته می‌گیرم و در صورت تأیید تهدید، اقدامات مهار و بهبود Detection را پیشنهاد می‌کنم.
