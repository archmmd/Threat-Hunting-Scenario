# سناریوی Threat Hunting: یک Admin Account روی Host غیرمعمول Login کرده

این سناریو برای مصاحبه‌ی SOC T2 و Threat Hunter مهم است؛ چون حساب‌های ادمین معمولاً دسترسی گسترده‌ای دارند و سوءاستفاده از آن‌ها می‌تواند به Privilege Abuse، Lateral Movement و در نهایت Domain Compromise منجر شود.

اما نکته‌ی اصلی این است: ورود یک Admin Account به Host غیرمعمول، یک Anomaly است؛ نه به‌تنهایی مدرک Compromise. باید بفهمیم ورود مجاز بوده، ناشی از تغییرات عملیاتی است یا بخشی از فعالیت مهاجم.

## 1. Hunt Objective & Hypothesis — هدف و فرضیه

هدف من این است که منشأ Login، مشروعیت آن و فعالیت‌های پس از ورود را مشخص کنم.

سه فرضیه‌ی اصلی:

- H1 — Credential Compromise: مهاجم اعتبارنامه‌ی ادمین را به دست آورده و از آن استفاده کرده است.
- H2 — Lateral Movement: ادمین یا مهاجم از یک سیستم اولیه به Host دیگری حرکت کرده است.
- H3 — Legitimate Activity: ورود مربوط به کار پشتیبانی، شیفت ادمین، Maintenance یا یک ابزار مدیریتی مجاز است.

برای شروع باید به این سؤال پاسخ بدهم: چه چیزی این Host را غیرمعمول کرده است؟ مثلاً حساب قبلاً فقط روی Jump Server وارد می‌شده، اما حالا از یک Workstation معمولی یا سروری خارج از محدوده‌ی مجاز Login کرده است.

## 2. Telemetry & Data Sources — منابع داده

Windows Security Logs

- `4624`: ورود موفق
- `4625`: ورود ناموفق
- `4648`: استفاده از اعتبارنامه‌های صریح
- `4672`: تخصیص Privilegeهای حساس به یک Logon Session
- `4688`: ایجاد Process

Network و Remote Access

لاگ‌های RDP، VPN، Firewall، DNS و در صورت وجود، لاگ‌های SMB و WinRM برای بررسی مسیر دسترسی و ارتباطات بین میزبان‌ها.

EDR و Identity Logs

Process Tree، فرمان‌های اجراشده، ایجاد سرویس یا Scheduled Task، تغییرات حساب‌ها و رویدادهای احراز هویت Active Directory یا سامانه‌ی هویتی سازمان.

### Logon Type را چطور تفسیر می‌کنم؟

| Logon Type | معنی               | نکته‌ی Hunting                                                         |
| ---------- | ------------------ | ---------------------------------------------------------------------- |
| `2`        | Interactive        | ورود محلی؛ بررسی کن آیا ادمین واقعاً باید روی آن Host کار کند.         |
| `3`        | Network            | دسترسی شبکه‌ای؛ ممکن است SMB یا سرویس‌های دیگر باشد و لزوماً RDP نیست. |
| `4`        | Batch              | اجرای Batch Job یا Scheduled Task                                      |
| `5`        | Service            | شروع یک سرویس                                                          |
| `10`       | Remote Interactive | معمولاً ورود از راه دور با RDP                                         |

`Logon Type` به‌تنهایی پروتکل یا نیت مهاجم را اثبات نمی‌کند. همچنین `4672` نشان‌دهنده‌ی Privilegeهای حساس در یک Session است، نه لزوماً فعالیت مخرب.

## 3. Hunt Execution & Queries — اجرای Hunt

### گام اول: پیدا کردن Loginهای ادمین

در Microsoft Sentinel می‌توانم با `SecurityEvent` ورودهای موفق را برای حساب موردنظر استخراج کنم:

```
let AdminAccount = @"CONTOSO\admin.user";
SecurityEvent
| where TimeGenerated > ago(7d)
| where EventID == 4624
| where TargetAccount =~ AdminAccount
| project
    TimeGenerated,
    Computer,
    TargetAccount,
    LogonType,
    IpAddress,
    WorkstationName,
    AuthenticationPackageName,
    TargetLogonId
| order by TimeGenerated desc
```

چه چیزی را بررسی می‌کنم؟

- آیا Host مقصد قبلاً در سابقه‌ی این حساب دیده شده است؟
- آیا Source IP یا Workstation مبدأ غیرمعمول است؟
- آیا Login در ساعتی خارج از الگوی کاری انجام شده؟
- آیا `LogonType` با روش معمول دسترسی ادمین تطابق دارد؟
- آیا قبل از Login، تلاش‌های ناموفق یا استفاده از اعتبارنامه‌های صریح ثبت شده است؟

> نام فیلدها و در دسترس بودنشان به روش جمع‌آوری لاگ و Connector بستگی دارد. اگر حساب در Domainهای مختلف نام‌گذاری متفاوتی داشته باشد، باید فیلتر را با فرمت واقعی لاگ تطبیق بدهم.

### گام دوم: پیدا کردن Hostهایی که برای حساب جدید هستند

برای مقایسه‌ی رفتار اخیر با سابقه‌ی موجود، می‌توانم از یک بازه‌ی طولانی‌تر به‌عنوان Baseline استفاده کنم:

```
let BaselineStart = ago(30d);
let RecentStart = ago(24h);
let AdminLogons =
    SecurityEvent
    | where TimeGenerated >= BaselineStart
    | where EventID == 4624
    | where isnotempty(TargetAccount)
    | project TimeGenerated, TargetAccount, Computer, LogonType, IpAddress;
let KnownHosts =
    AdminLogons
    | where TimeGenerated < RecentStart
    | summarize by TargetAccount, Computer;
AdminLogons
| where TimeGenerated >= RecentStart
| join kind=leftanti KnownHosts on TargetAccount, Computer
| order by TimeGenerated desc
```

این Query ورودهای ۲۴ ساعت اخیر را نشان می‌دهد که ترکیب حساب و Host مقصد در ۲۹ روز قبلیِ Baseline دیده نشده است.

محدودیت مهم: این نتیجه فقط یعنی ترکیب موردنظر در بازه‌ی جمع‌آوری‌شده مشاهده نشده؛ نه اینکه حساب قطعاً قبلاً هرگز به آن Host وارد نشده باشد. برای Baseline معتبرتر، به Retention کافی، پوشش کامل لاگ‌ها و شناخت تغییرات عملیاتی نیاز دارم.

### گام سوم: بررسی فعالیت بعد از Login

اگر Login مشکوک باشد، بررسی را متوقف نمی‌کنم. باید مشخص کنم ادمین پس از ورود چه کارهایی انجام داده است:

- آیا Processهایی مثل `powershell.exe`، `cmd.exe` یا ابزارهای مدیریتی اجرا شده‌اند؟
- آیا سرویس جدید، Scheduled Task یا حساب کاربری جدید ایجاد شده است؟
- آیا به Hostهای دیگر متصل شده یا به منابع حساس دسترسی پیدا کرده است؟
- آیا تلاش برای غیرفعال‌کردن ابزارهای امنیتی، دست‌کاری لاگ‌ها یا تغییر مجوزها دیده می‌شود؟

اگر Microsoft Defender XDR در دسترس باشد، برای بررسی Processها می‌توانم از `DeviceProcessEvents` استفاده کنم:

```
DeviceProcessEvents
| where Timestamp > ago(24h)
| where DeviceName =~ "unusual-host.contoso.com"
| where AccountName =~ "admin.user"
| project
    Timestamp,
    DeviceName,
    AccountName,
    FileName,
    ProcessCommandLine,
    InitiatingProcessFileName,
    InitiatingProcessCommandLine
| order by Timestamp desc
```

این Query یک نقطه‌ی شروع است، نه اثبات رابطه‌ی قطعی بین رویداد Login و هر Process. باید زمان‌ها، شناسه‌های Session در صورت وجود، Process Tree و داده‌های EDR را با هم تطبیق بدهم.

## 4. Pivoting & Evidence Correlation — همبستگی شواهد

پس از پیدا کردن Login مشکوک، روی چند محور Pivot می‌کنم:

Admin Account + Host غیرمعمول

مبدأ دسترسی

Source IP، Workstation، VPN، Jump Server

نوع ورود

Logon Type، زمان، Session، روش احراز هویت

فعالیت پس از ورود

Processها، سرویس‌ها، Taskها، تغییرات دسترسی

گسترش فعالیت

Loginهای مشابه روی Hostهای دیگر و دسترسی به منابع حساس

مثال: اگر حساب ادمین از یک Workstation معمولی وارد سرور حساس شده باشد و سپس PowerShell اجرا کند، این دو رویداد در کنار هم مشکوک‌ترند. اگر همان Session پس از آن به چند سرور دیگر دسترسی پیدا کند و سرویس غیرمجاز بسازد، فرضیه‌ی Lateral Movement قوی‌تر می‌شود.

با این حال، اجرای PowerShell یا دسترسی چندسروری می‌تواند بخشی از عملیات مجاز باشد. برای نتیجه‌گیری، باید زمان‌بندی، فرمان‌ها، مبدأ، مجوزها و تأیید مالک سیستم را بررسی کنم.

## 5. Validation & Scope — اعتبارسنجی و تعیین دامنه

قبل از اعلام Incident، این موارد را بررسی می‌کنم:

1. تأیید فعالیت مجاز: آیا Change Ticket، عملیات Maintenance یا تأیید مالک سیستم وجود دارد؟
2. اعتبار مبدأ: آیا Source IP متعلق به VPN، Jump Server یا سیستم مدیریتی مجاز است؟
3. بررسی حساب: آیا حساب واقعاً Admin است؟ چه سطح دسترسی و چه محدوده‌ای دارد؟ آیا استفاده‌ی اشتراکی از حساب وجود دارد؟
4. گسترش دامنه: آیا همین حساب از همان مبدأ یا با الگوی مشابه روی Hostهای دیگر هم استفاده شده است؟
5. بررسی شواهد مستقل: آیا علاوه بر Login غیرعادی، نشانه‌هایی از اجرای فرمان مشکوک، ایجاد Persistence، تغییر مجوز یا دسترسی غیرمجاز وجود دارد؟

در نهایت یافته را در یکی از این سطوح گزارش می‌کنم:

- Anomaly: ورود با Baseline یا سیاست دسترسی تفاوت دارد.
- Suspicious Activity: شواهد تکمیلی، احتمال سوءاستفاده را تقویت می‌کنند.
- Confirmed Compromise: شواهد قابل اتکا استفاده‌ی غیرمجاز یا فعالیت مخرب را تأیید می‌کنند.

## 6. MITRE ATT&CK Mapping

تکنیک‌ها را بر اساس رفتار مشاهده‌شده نگاشت می‌کنم، نه صرفاً به‌خاطر اینکه حساب Admin بوده است.

| تکنیک                                | چه زمانی مرتبط است؟                                                                 |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| T1078 — Valid Accounts               | وقتی شواهد نشان دهد از حساب معتبر برای دسترسی غیرمجاز استفاده شده است.              |
| T1021 — Remote Services              | وقتی دسترسی از طریق یک سرویس راه دور تأیید شود.                                     |
| T1021.001 — Remote Desktop Protocol  | وقتی استفاده از RDP شواهد کافی داشته باشد.                                          |
| T1021.002 — SMB/Windows Admin Shares | وقتی حرکت یا دسترسی از طریق SMB/Admin Shares تأیید شود.                             |
| T1059.001 — PowerShell               | وقتی اجرای PowerShell مشاهده شود و برای رفتار مورد بررسی مرتبط باشد.                |
| T1562.001 — Impair Defenses          | وقتی شواهدی از تلاش برای غیرفعال‌کردن یا مختل‌کردن دفاع‌های امنیتی وجود داشته باشد. |

نکته: رویداد `4624` به‌تنهایی هیچ‌یک از این تکنیک‌ها را قطعی نمی‌کند. نگاشت باید متناسب با شواهد و جزئیات رفتار باشد.

## 7. Conclusion & Confidence — نتیجه‌گیری و سطح اطمینان

فرض کنیم این شواهد را پیدا کرده‌ام:

- حساب ادمین روی Hostی Login کرده که در Baseline اخیر آن دیده نشده است.
- مبدأ ورود، Workstation معمولی است و نه Jump Server سازمان.
- پس از Login، یک فرمان PowerShell غیرمعمول اجرا شده است.
- همان حساب مدت کوتاهی بعد به دو سرور دیگر دسترسی پیدا کرده است.

این مجموعه شواهد، فرضیه‌ی استفاده‌ی غیرمجاز از اعتبارنامه و احتمال Lateral Movement را تقویت می‌کند؛ اما هنوز باید محتوای فرمان، مجاز بودن فعالیت و ارتباط Sessionها را بررسی کنم.

سطح اطمینان را با توجه به کیفیت و استقلال شواهد تعیین می‌کنم:

- اگر فقط Host غیرمعمول باشد: اطمینان پایین تا متوسط به وجود فعالیت مشکوک.
- اگر مبدأ غیرمعمول و فعالیت پس از Login هم دیده شود: اطمینان بالاتر به وجود فعالیت مشکوک.
- اگر استفاده‌ی غیرمجاز از حساب و رفتار مخرب با شواهد معتبر تأیید شود: Incident تأییدشده.

این سطوح کیفی‌اند، نه احتمال عددی؛ همچنین اطمینان به مشکوک‌بودن فعالیت با اطمینان به Compromise یکی نیست.

## 8. Response & Detection Improvement — واکنش و بهبود Detection

اگر شواهد نشان دهد احتمال سوءاستفاده جدی است، مطابق رویه‌ی Incident Response سازمان اقدام می‌کنم:

1. Containment: در صورت نیاز و با هماهنگی تیم مسئول، Session را خاتمه می‌دهم، حساب را محدود یا موقتاً غیرفعال می‌کنم و اعتبارنامه‌ها را امن‌سازی می‌کنم. برای حساب‌های حساس، اثر جانبی روی سرویس‌های حیاتی را در نظر می‌گیرم.
2. Scope: حساب، مبدأ، Host مقصد و سرورهای دیگری را که ممکن است درگیر شده باشند بررسی می‌کنم.
3. Evidence Preservation: لاگ‌ها، Process Tree، زمان‌ها و شواهد EDR را برای تحلیل و بررسی بعدی حفظ می‌کنم.
4. Detection Improvement: به‌جای Alert ساده برای هر Login ادمین، چند سیگنال را ترکیب می‌کنم:
   - نوع حساب و سطح دسترسی
   - Host مقصد و میزان انحراف از Baseline
   - مبدأ دسترسی و Logon Type
   - زمان و سابقه‌ی رفتار
   - فعالیت‌های بعد از Login، مثل اجرای فرمان یا ایجاد سرویس

هدف این است که هم احتمال تشخیص سوءاستفاده را افزایش بدهم و هم False Positive ناشی از عملیات مجاز ادمین‌ها را کاهش دهم.

## پاسخ کوتاه برای شروع جواب در مصاحبه

ابتدا Event ID 4624 را بررسی می‌کنم تا مشخص شود Admin Account از چه مبدأیی، در چه زمانی و با چه Logon Type روی Host غیرمعمول وارد شده است. سپس این فعالیت را با Baseline حساب، محدوده‌ی دسترسی مجاز و برنامه‌ی نگهداری سازمان مقایسه می‌کنم.

در مرحله‌ی بعد، با بررسی رویدادهای 4625، 4648 و 4672 و همچنین Telemetry مربوط به Processها و ارتباطات شبکه، فعالیت قبل و بعد از Login را تحلیل می‌کنم. اگر شواهدی از اجرای فرمان مشکوک، دسترسی به سرورهای دیگر یا ایجاد Persistence وجود داشته باشد، Hunt را روی سایر میزبان‌ها گسترش می‌دهم.

در صورت مشاهده‌ی شواهد مرتبط، تکنیک‌های مناسب MITRE ATT&CK مانند Valid Accounts و Remote Services را بررسی می‌کنم. اگر احتمال Compromise جدی باشد، اقدامات مهار را متناسب با ریسک و رویه‌ی سازمان انجام می‌دهم.

نکته‌ی مهم این است که Login یک Admin Account روی Host غیرمعمول به‌تنهایی اثبات‌کننده‌ی حمله نیست؛ تصمیم نهایی باید بر اساس همبستگی شواهد، اعتبارسنجی فعالیت مجاز و دامنه‌ی تأثیر باشد.
