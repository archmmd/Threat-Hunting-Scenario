# سناریوی Threat Hunting: چندین Event ID 4625 و سپس یک 4624 موفق

این یکی از سناریوهای کلاسیک مصاحبه‌ی SOC T2 است؛ چون ممکن است نشان‌دهنده‌ی Brute Force، Password Spraying یا تلاش برای دسترسی غیرمجاز با یک حساب کاربری باشد.

اما نکته‌ی مهم این است: چند ورود ناموفق و سپس یک ورود موفق، به‌تنهایی اثبات نمی‌کند که مهاجم وارد سیستم شده است. باید بررسی کنیم تلاش‌ها از کجا آمده‌اند، کدام حساب‌ها هدف بوده‌اند، ورود موفق از چه نوعی بوده و آیا پس از آن فعالیت مشکوکی رخ داده است.

## 1. Hunt Objective & Hypothesis — هدف و فرضیه

هدف من مشخص کردن این است که آیا رویدادهای ورود ناموفق و موفق بخشی از رفتار عادی کاربر هستند یا نشانه‌ی تلاش برای دسترسی غیرمجاز.

چهار فرضیه‌ی اصلی دارم:

- H1 — Brute Force: مهاجم رمزهای متعددی را برای یک حساب امتحان کرده و در نهایت موفق شده است.
- H2 — Password Spraying: یک یا چند رمز رایج روی حساب‌های متعدد امتحان شده‌اند و یکی از تلاش‌ها موفق شده است.
- H3 — دسترسی غیرمجاز با اعتبارنامه‌ی معتبر: حساب کاربری در معرض خطر بوده و پس از ورود موفق برای فعالیت دیگری استفاده شده است.
- H4 — رفتار عادی: کاربر رمز خود را اشتباه وارد کرده، کلاینت یا سرویس تلاش‌های مجدد انجام داده یا یک مشکل پیکربندی باعث رویدادهای ناموفق شده است.

در ابتدا مشخص می‌کنم آیا 4625ها و 4624 مربوط به همان حساب، همان میزبان، همان مبدأ و یک بازه‌ی زمانی معنادار هستند یا فقط از نظر زمانی نزدیک‌اند.

## 2. Telemetry & Data Sources — چه داده‌هایی لازم دارم؟

Windows Security Event Log

Event ID 4625 و Event ID 4624

نام حساب، زمان، Logon Type، Source Network Address، Workstation Name، Authentication Package، Status و SubStatus.

شبکه و زیرساخت احراز هویت

VPN، Firewall، RDP Gateway، Domain Controller و در صورت وجود NPS

برای تشخیص مبدأ تلاش‌ها، مسیر دسترسی و اینکه ورود از شبکه‌ی داخلی، VPN یا اینترنت انجام شده است.

فعالیت پس از ورود موفق

EDR، Process Creation، نشست‌های کاربری و رویدادهای دسترسی

برای بررسی اجرای ابزارهای غیرمعمول، ارتباطات شبکه‌ای، تغییرات حساب و احتمال حرکت جانبی.

### تفاوت مهم این دو Event ID

| Event ID | معنی                                  | نکته‌ی تحلیلی                                       |
| -------- | ------------------------------------- | --------------------------------------------------- |
| 4625     | An account failed to log on           | ورود ناموفق؛ باید علت شکست و نوع ورود را بررسی کرد. |
| 4624     | An account was successfully logged on | ورود موفق؛ اما لزوماً به معنای موفقیت حمله نیست.    |

فیلدهای مهم در این سناریو:

- `TargetUserName`: حساب هدف
- `IpAddress`: آدرس مبدأ، در صورت ثبت
- `LogonType`: نوع ورود
- `Status` و `SubStatus`: علت شکست احراز هویت
- `AuthenticationPackageName`: روش یا بسته‌ی احراز هویت
- `TargetLogonId`: شناسه‌ی نشست ورود موفق، برای Pivot کردن به برخی رویدادهای بعدی

محدودیت: ممکن است بعضی فیلدها خالی یا ناقص باشند. همچنین رویداد 4624 روی میزبان مقصد یا سامانه‌ای که احراز هویت را ثبت کرده باید در زمینه‌ی درست تحلیل شود؛ صرفاً کنار هم قرار دادن رویدادها بدون توجه به محل ثبت آن‌ها می‌تواند گمراه‌کننده باشد.

## 3. Hunt Execution & Queries — اجرای عملی Hunt

### مرحله‌ی اول: بررسی رویدادهای 4625 و 4624

اگر لاگ‌های Windows Security در Microsoft Sentinel و جدول `SecurityEvent` در دسترس باشند، با این Query شروع می‌کنم:

```
SecurityEvent
| where TimeGenerated > ago(24h)
| where EventID in (4624, 4625)
| project
    TimeGenerated,
    Computer,
    EventID,
    TargetAccount,
    TargetUserName,
    IpAddress,
    WorkstationName,
    LogonType,
    Status,
    SubStatus,
    AuthenticationPackageName,
    Activity
| order by TimeGenerated desc
```

هدف در این مرحله شناسایی الگو است، نه اعلام قطعی حمله. بررسی می‌کنم:

- آیا چندین شکست برای یک حساب کاربری ثبت شده است؟
- آیا شکست‌ها از یک IP یا چند IP آمده‌اند؟
- آیا پس از شکست‌ها، ورود موفق از همان مبدأ یا مبدأ متفاوت ثبت شده است؟
- آیا `LogonType` با دسترسی مورد انتظار سازگار است؟
- آیا `Status` و `SubStatus` نشان‌دهنده‌ی رمز اشتباه، حساب غیرفعال یا علت دیگری هستند؟

نکته‌ی فنی: Schema جدول `SecurityEvent` بسته به نوع اتصال و پیکربندی ممکن است متفاوت باشد. اگر بعضی ستون‌ها موجود نباشند، باید Query را با Schema واقعی Workspace تطبیق دهم.

### مرحله‌ی دوم: پیدا کردن ورود موفق پس از چند شکست

در این Query، ابتدا تعداد شکست‌ها را بر اساس میزبان، حساب و مبدأ در پنجره‌های زمانی پنج‌دقیقه‌ای می‌شمارم و سپس ورود موفق را در همان گروه بررسی می‌کنم.

```
let FailedLogons =
    SecurityEvent
    | where TimeGenerated > ago(24h)
    | where EventID == 4625
    | summarize
        FailedCount = count(),
        FirstFailure = min(TimeGenerated),
        LastFailure = max(TimeGenerated)
        by Computer, TargetAccount, IpAddress,
           Window = bin(TimeGenerated, 5m);
let SuccessfulLogons =
    SecurityEvent
    | where TimeGenerated > ago(24h)
    | where EventID == 4624
    | project
        Computer,
        TargetAccount,
        IpAddress,
        SuccessTime = TimeGenerated,
        LogonType;
FailedLogons
| where FailedCount >= 5
| join kind=inner SuccessfulLogons
    on Computer, TargetAccount, IpAddress
| where SuccessTime >= FirstFailure
| where SuccessTime <= FirstFailure + 15m
| project
    Computer,
    TargetAccount,
    IpAddress,
    FailedCount,
    FirstFailure,
    LastFailure,
    SuccessTime,
    LogonType
| order by SuccessTime desc
```

این Query یک نقطه‌ی شروع است، نه یک Detection کامل. محدودیت مهم آن این است که شکست‌ها را در پنجره‌های پنج‌دقیقه‌ای گروه‌بندی می‌کند؛ در نتیجه ممکن است شکست‌هایی که از مرز دو پنجره عبور می‌کنند از هم جدا شوند. همچنین اگر IP در رویداد موفق خالی یا متفاوت باشد، الگو را از دست می‌دهد.

در بررسی کامل‌تر، همبستگی را بر اساس حساب و زمان انجام می‌دهم و سپس مبدأ و مقصد را جداگانه اعتبارسنجی می‌کنم؛ نباید فقط به یکسان بودن IP متکی باشم.

### مرحله‌ی سوم: تشخیص تفاوت Brute Force و Password Spraying

| الگوی مشاهده‌شده                                  | فرضیه‌ی محتمل                                   |
| ------------------------------------------------- | ----------------------------------------------- |
| شکست‌های زیاد برای یک حساب از یک مبدأ             | Brute Force یا اشتباهات مکرر کاربر              |
| تلاش برای حساب‌های متعدد از یک مبدأ در زمان کوتاه | Password Spraying یا فعالیت خودکار              |
| شکست‌های زیاد از چند مبدأ برای یک حساب            | توزیع‌شده بودن حمله، سرویس معیوب یا چند کلاینت  |
| ورود موفق پس از شکست‌ها، همراه با فعالیت غیرعادی  | احتمال دسترسی غیرمجاز؛ نیازمند اعتبارسنجی بیشتر |

برای Password Spraying، تعداد حساب‌های یکتا در کنار تعداد شکست‌ها را بررسی می‌کنم؛ چون تمرکز صرف بر یک حساب ممکن است این الگو را از قلم بیندازد.

## 4. Pivoting & Evidence Correlation — هم‌بسته‌سازی شواهد

پس از پیدا کردن الگو، از رویدادهای ورود به شواهد تکمیلی Pivot می‌کنم.

4625 — Failed Logons

تعداد، حساب هدف، مبدأ و علت شکست

4624 — Successful Logon

مبدأ، مقصد، Logon Type و زمان ورود

Account

سطح دسترسی، حساب‌های هدف و تغییرات اخیر

Source

IP، VPN، دستگاه مبدأ و سابقه‌ی آن

Session

نشست موفق و رویدادهای مرتبط با Logon ID

Post-Logon

اجرای Process، دسترسی به منابع و حرکت جانبی

سؤالاتی که باید پاسخ بدهم:

1. آیا IP مبدأ متعلق به VPN یا دستگاه مجاز کاربر است؟
2. آیا نوع ورود، مثلاً ورود تعاملی یا شبکه‌ای، با الگوی کاری حساب سازگار است؟
3. آیا حساب موردنظر حساب کاربری عادی، ادمین یا Service Account است؟
4. آیا بعد از ورود موفق، فعالیت غیرمعمولی روی سیستم مقصد مشاهده شده است؟
5. آیا همین مبدأ حساب‌های دیگر را نیز هدف قرار داده است؟

برای بررسی رویدادهای بعد از ورود، `TargetLogonId` در Event ID 4624 می‌تواند در صورت وجود و تطبیق صحیح با میزبان و زمان، به همبسته‌سازی رویدادهای مرتبط کمک کند. این شناسه را نباید به‌تنهایی و بدون توجه به میزبان استفاده کرد.

## 5. Validation & Scope — اعتبارسنجی و تعیین گستره

پیش از نتیجه‌گیری، چهار مورد را مشخص می‌کنم:

- علت شکست‌ها: آیا Status و SubStatus با رمز اشتباه یا علت دیگری سازگارند؟
- اعتبار ورود موفق: آیا کاربر ورود را تأیید می‌کند و آیا دستگاه و زمان ورود منطقی هستند؟
- گستره: آیا حساب‌های دیگر یا میزبان‌های دیگر نیز درگیر هستند؟
- اثر احتمالی: آیا پس از ورود موفق، تغییرات حساب، اجرای ابزارهای مدیریتی غیرعادی یا دسترسی مشکوک به منابع مشاهده شده است؟

برای مثال، پنج ورود ناموفق از یک IP عمومی و سپس ورود موفق برای حساب ادمین، از نظر اولویت بررسی مهم است؛ اما اگر آن IP متعلق به VPN سازمان باشد و کاربر رمز خود را اشتباه وارد کرده باشد، تفسیر متفاوتی خواهیم داشت.

شواهدی که باید از هم تفکیک شوند:

- ورود ناموفق: مشاهده‌شده
- ورود موفق: مشاهده‌شده
- دسترسی مهاجم: هنوز نیازمند اثبات
- سوءاستفاده از حساب یا انجام فعالیت مخرب: نیازمند شواهد تکمیلی

## 6. MITRE ATT&CK Mapping — نگاشت احتمالی

| تکنیک                         | چه زمانی مناسب است؟                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------- |
| T1110 — Brute Force           | زمانی که شواهد با تلاش‌های تکراری برای حدس‌زدن اعتبارنامه سازگار باشند.               |
| T1110.003 — Password Spraying | زمانی که یک یا چند رمز روی حساب‌های متعدد امتحان شده باشند.                           |
| T1078 — Valid Accounts        | زمانی که شواهد نشان دهند از حساب معتبر برای دسترسی یا فعالیت غیرمجاز استفاده شده است. |

صرف وجود 4625 و 4624 برای نسبت دادن قطعی تکنیک کافی نیست. به‌ویژه T1078 زمانی معنا پیدا می‌کند که شواهد استفاده‌ی غیرمجاز از حساب معتبر وجود داشته باشد؛ هر ورود موفقی حمله محسوب نمی‌شود.

## 7. Conclusion & Confidence — نتیجه‌گیری و سطح اطمینان

نتیجه‌ی Hunt را در یکی از این دسته‌ها قرار می‌دهم:

- Suspicious: چندین ورود ناموفق و سپس ورود موفق دیده شده، اما منشأ و ماهیت آن هنوز مشخص نیست.
- Likely Compromise: الگوی ورود، مبدأ غیرمنتظره و رفتار پس از ورود با دسترسی غیرمجاز سازگار است، ولی برخی شواهد هنوز نیازمند تأییدند.
- Confirmed Compromise: شواهد معتبر نشان می‌دهند حساب یا نشست واقعاً برای دسترسی غیرمجاز استفاده شده است.

در گزارش نهایی، تعداد شکست‌ها، زمان اولین و آخرین شکست، زمان ورود موفق، حساب، IP مبدأ، مقصد، Logon Type، علت شکست‌ها و شواهد فعالیت پس از ورود را ثبت می‌کنم.

## 8. Response & Detection Improvement — واکنش و بهبود Detection

اگر احتمال دسترسی غیرمجاز جدی باشد، متناسب با سیاست سازمان:

1. وضعیت حساب و نشست فعال را بررسی می‌کنم و در صورت لزوم نشست‌ها را باطل یا حساب را موقتاً محدود می‌کنم.
2. در صورت تأیید یا وجود خطر فوری، اعتبارنامه‌ها را طبق رویه‌ی سازمان ایمن می‌کنم و میزبان‌های درگیر را بررسی یا مهار می‌کنم.
3. سایر حساب‌ها و دستگاه‌ها را برای الگوی مشابه Hunt می‌کنم.
4. Detection را بر اساس تعداد شکست‌ها، حساب‌های یکتا، تنوع IPها، نوع ورود و موفقیت پس از شکست‌ها بهبود می‌دهم.
5. در صورت امکان، کنترل‌های پیشگیرانه مانند MFA، محدودیت تلاش‌های ورود و سیاست‌های دسترسی را ارزیابی می‌کنم.

نباید صرفاً به دلیل چند 4625 حساب را مسدود کرد؛ این کار ممکن است موجب اختلال سرویس یا قفل شدن حساب کاربر قانونی شود. تصمیم باید بر اساس ریسک و شواهد باشد.

## پاسخ کوتاه برای شروع جواب در مصاحبه

ابتدا Event ID 4625 و 4624 را بررسی می‌کنم تا مشخص شود چند تلاش ناموفق رخ داده، کدام حساب هدف بوده و ورود موفق از چه مبدأ و با چه Logon Type ثبت شده است.

سپس Status و SubStatus رویدادهای ناموفق را بررسی می‌کنم و تلاش‌ها را بر اساس حساب، IP مبدأ، میزبان و زمان هم‌بسته می‌کنم تا احتمال Brute Force یا Password Spraying را ارزیابی کنم.

بعد از ورود موفق، فعالیت نشست و رویدادهای مرتبط را بررسی می‌کنم تا مشخص شود آیا دسترسی غیرمجاز یا رفتار مشکوکی رخ داده است. در ادامه، Hunt را به سایر حساب‌ها و میزبان‌ها گسترش می‌دهم.

نکته‌ی مهم این است که چند ورود ناموفق و یک ورود موفق به‌تنهایی اثبات‌کننده‌ی Compromise نیست. نتیجه‌گیری و اقدامات مهار را بر اساس شواهد معتبر، میزان ریسک و رفتار پس از ورود انجام می‌دهم.
